## Oracle Analysis: Extraction Profile Proposal & Review Overhaul

### Diagnosis: What's actually broken

The proposal generator has a **fundamental architectural flaw**: it constrains the LLM to pick from heuristic-discovered candidates rather than letting it inspect the actual page structure. This means:

1. **Image discovery fails** because the heuristic scanner misses Dawn-theme patterns like `.product__media-wrapper`, `.product__media-item`, `[data-product-single-media-wrapper]` — and the LLM can't propose a selector it wasn't shown.

2. **The review UI is selector-centric, not outcome-centric.** The user thinks "did it extract 'Pupsicle' + 'Small' + 'Tie Dye' + 4 images?" but the UI asks "do you approve `h1.product__title`?" That's an implementation detail the operator shouldn't need to judge.

3. **The generate → validate → approve flow is disjointed.** Three separate buttons across two tabs, with no feedback loop. The user generates, switches tabs to validate, switches back to approve. There's no "here's what your profile would extract — looks right?" moment.

4. **The system ignores Shopify productJSON.** The existing `page-extractor.ts` already extracts variants, images, titles, and descriptions from embedded `window.productJSON` — successfully for mywoof.com. But the proposal generator doesn't know about this. It only proposes CSS selectors, missing the richest data source on Shopify sites.

5. **Price and Brand linger as ghosts.** We removed them from the LLM prompt, but `SELECTOR_FIELDS` still includes them, the review table still renders rows for them, and the approval flow still treats them as fields.

### Answers to your five questions

**Q1: Should the proposal generator be more interactive?**

**No — but the review should be.** Making the LLM ask clarifying questions adds latency, complexity, and prompt-injection surface area. The LLM should do its job in one shot. What should be interactive is the **review**: the operator sees the extracted data, says "that title is wrong" or "those images include a logo," and the system generates a revised proposal from that feedback. This is the existing `StructuredFeedback` mechanism — it just needs to be connected to a preview-driven UI instead of a selector-approval UI.

**Q2: Should the LLM inspect the full HTML and write its own selectors?**

**Yes, with guardrails.** The current "pick from candidates" approach is the bottleneck. The LLM should receive the minimized HTML (or a structured representation of it) and write selectors directly. The guardrails are:
- Validate every returned selector against the HTML (must match at least one element)
- Reject browser-only pseudo-selectors (`:has()`, `:is()`) — keep the existing `isSupportedSelectorSyntax` check
- Cap the HTML size (keep `MAX_MINIMIZED_BYTES`)
- Keep the JSON-only output format

This is a one-line change to the prompt: "Write the best CSS selector for each field" instead of "Choose from the candidate list." The candidate list can still be provided as hints, but the LLM should be free to write selectors it didn't see in the list.

**Q3: Should we pivot to preview-driven review?**

**Yes — this is the single highest-impact change.** Instead of showing a table of selectors with pass/warn/fail badges, show:
- The extracted title (as text)
- The extracted description (as text, truncated)
- The extracted images (as thumbnail grid)
- The detected variant options (as pills: "Small", "Tie Dye")
- A "looks right?" approval button + a "something's wrong" feedback button

The operator approves the **output**, not the **selectors**. If the output is wrong, they click "something's wrong" and describe what's incorrect. The system generates a revised proposal from that feedback. This is simpler, faster, and more reliable than asking the operator to evaluate CSS selector quality.

**Q4: Should we merge generate + validate + approve into one flow?**

**Yes.** The current three-step disjointed flow should become:
1. Operator enters a seed URL (or it's pre-filled from a blocked item)
2. System fetches the page, generates a proposal, and **immediately runs it against the seed URL**
3. UI shows the extracted data preview (title, description, images, variants)
4. Operator says "looks right" → system validates across other confirmed samples → shows aggregate results → operator approves
5. Or operator says "wrong" → describes what's incorrect → system regenerates → back to step 3

This is a single conversational loop, not three separate tabs.

**Q5: Should we pivot to a fundamentally different approach (vision model, Stagehand)?**

**Not yet.** The current CSS-selector approach is correct for deterministic trusted extraction. Vision models and Stagehand are for the **builder** side (discovery and proposal), not the **extraction** side. The improvement needed is:
- Let the LLM write selectors from the HTML directly (not just pick from candidates)
- Add Shopify productJSON as a first-class extraction strategy (not just CSS selectors)
- Preview the extracted data before asking for approval

Stagehand's `observe`/`extract` primitives could help the builder propose selectors more reliably, but that's Phase 6 (already deferred) and doesn't block the improvements above.

### Concrete recommendation: The path forward

**Phase A — Fix the proposal generator (backend, ~2 hours)**

1. **Change the LLM prompt** from "choose from candidates" to "write the best CSS selector." Keep candidates as hints but don't constrain the LLM to them.
2. **Add a Shopify productJSON strategy** to `GeneratedSelectorProfile`. When the page has `window.productJSON`, the proposal should include `"extractionStrategy": "shopify_json"` alongside the CSS selectors. The trusted extractor already uses this data — the profile should formalize it.
3. **Remove price/brand from `SELECTOR_FIELDS`** entirely. Remove the rows from the review table. Remove the approval/rejection buttons for those fields. Clean up `ProfileFieldValidationTable` to only show title, description, and images.
4. **Add a `seedUrlPreview` to the generation flow**: after generating, immediately run the proposed selectors against the seed URL and store the extracted data alongside the proposal. This becomes the preview the review UI shows.

**Phase B — Preview-driven review UI (~3 hours)**

5. **Replace the selector-approval table with an extraction preview panel.** Show:
   - Extracted title (large text)
   - Extracted description (truncated paragraph)
   - Extracted images (thumbnail grid, reusing `ImagePreviewGrid`)
   - Detected variant options (pills)
   - "This looks correct" button → triggers cross-sample validation → shows aggregate pass/fail → enables promotion
   - "Something's wrong" button → opens a simple feedback form (what's wrong with title? what's wrong with images?) → triggers regeneration

6. **Merge the Proposals and Validation tabs** in `ProfileBuilderWorkspace` into a single "Review" flow that goes: generate → preview → validate → approve.

**Phase C — Variant strategy in the review UI (~1 hour)**

7. **Surface the variant selection strategy in the preview.** When `variantSelectionStrategy` is non-null, show the detected options and the container selector. Let the operator verify the options match what they see on the page.

### Why this approach

- **Reliability**: Letting the LLM write selectors from the HTML directly solves the image discovery problem without enumerating every possible Shopify theme pattern.
- **User experience**: Preview-driven review is dramatically simpler for the operator. They verify data, not CSS.
- **Implementation effort**: Phase A is mostly prompt changes + one new field. Phase B is UI reorganization, not new infrastructure. Phase C is surfacing existing data.
- **Maintainability**: Fewer heuristic patterns to maintain. The LLM adapts to new themes. The review UI doesn't need to understand CSS.
- **No new dependencies**: No Stagehand, no vision model, no new worker endpoints. Uses existing infrastructure.

### What not to do

- **Don't make the LLM interactive/conversational.** One-shot generation with feedback-driven regeneration is simpler and more reliable.
- **Don't pivot to vision models for proposal generation.** CSS selectors + Shopify JSON are deterministic and sufficient.
- **Don't try to enumerate every Shopify theme pattern.** Let the LLM read the HTML and write selectors.
- **Don't remove the candidate discovery entirely.** Keep it as hints for the LLM — it improves selector stability. Just don't constrain the LLM to only those candidates.
