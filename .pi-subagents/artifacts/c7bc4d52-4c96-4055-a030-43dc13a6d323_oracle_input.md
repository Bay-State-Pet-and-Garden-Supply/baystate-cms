Task:
We need to fundamentally rethink the extraction profile proposal generation and review system. Here's the context:

## Current state

The proposal generator (`src/onboarding/profile-generator.ts`) works like this:
1. Minimizes the page HTML (strips header/footer/nav/select/button/input/etc)
2. Scopes to a product container (main, .product, .product-detail, .pdp, etc.)
3. Scans for CSS selector candidates (title, description, image patterns)
4. Sends candidates to an LLM, which returns a JSON with selectors
5. Those selectors become a "profile generation" that a human must approve per-field

The review process (`src/client/components/ProfileProposalDrawer.tsx`, `ProfileGenerationReview.tsx`) shows the proposed selectors in a drawer. The human can approve/reject individual fields.

## What's broken

1. **Price and Brand selectors are now removed** (we import those from spreadsheet/brand mapping), but the review UI still shows Price and Brand fields, the selector values are null, and it wastes space
2. **Image discovery is weak** — even with expanded patterns, the LLM frequently returns null for imagesSelector because the selected patterns don't match the actual page structure. For mywoof.com, the product images use selectors like `.product__media-wrapper img` or similar Dawn-theme patterns that we may still not cover
3. **Variants** — We added variant discovery, but the extractor doesn't execute it yet, and the review UI has no section for reviewing the variant strategy. The proposed strategy exists in the generation JSON but isn't surfaced in the review drawer
4. **The review UI is field-based** (approve/reject per selector) but the user thinks in terms of "does this profile correctly extract the product data?" not "do I approve this CSS selector?"
5. **No way to test the proposal interactively** — the user generates a proposal, then separately has to run validation across samples, then go back to review. The flow is disjointed

## What the user wants

To generate a viable extraction profile for a Shopify product page like:
https://mywoof.com/products/pupsicle?variant=44913957470404

They want to extract:
- Product name: "Pupsicle"
- Size/option: "Small"
- Color/option: "Tie Dye"  
- Description: "Long-lasting quiet in a beautifully designed dog toy."
- 4 product images

## Questions for you

1. Should we make the proposal generator more interactive — let the AI ask clarifying questions, or let the operator guide it? Or keep it fully automated but improve the heuristics?

2. The current approach of "minimize DOM → discover candidates → LLM picks selectors" is fundamentally limited because the LLM can only pick from what the heuristic scanning discovers. Should we instead let the LLM inspect the full/minimized HTML directly and write its own selectors? Or keep the two-phase approach but dramatically improve the scanning?

3. The review UI is field-selector-approval oriented. Should we pivot to a "preview-driven" review where the user sees the extracted data (title, description, image thumbnails) and approves the output, not the selectors?

4. Should we merge the "Generate proposal" + "Validate across samples" + "Approve fields" flow into a single conversational/interactive pipeline?

5. Given the current limitations of the proposal generator, is it worth investing in improving it, or should we pivot to a fundamentally different approach (e.g., use the worker's Playwright snapshot + a vision model to identify page regions, or use Stagehand's observe/extract primitives)?
