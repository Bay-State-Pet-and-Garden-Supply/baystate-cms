# Store classification configuration under store/classification

Classification configuration will live in the workspace under `store/classification/` rather than in product files or SQLite-only state. This keeps Product Types, Product Attributes, Attribute Profiles, Attribute Mappings, guidance, and model/data-sharing policy versioned with the rest of store configuration while allowing SQLite to remain an index/cache for UI and classifier execution.

The configuration should be split into focused files, such as `product-types.json`, `attributes.json`, `attribute-profiles.json`, `mappings.json`, `guidance.json`, `model-policies.json`, and `data-sharing.json`, so reviews and merges are easier than with one large JSON file. A `manifest.json` should record the overall classification configuration compatibility version, and each focused file should also carry its own `schemaVersion` so migrations can target only the changed area. Product Types, Product Attributes, and Attribute Profiles should use stable human-readable IDs/slugs so Git diffs and cross-file references stay understandable; generated IDs are reserved for local operational records such as runs and history entries. Stable IDs should be immutable after creation; labels can change freely, but an ID rename is an explicit migration that updates references and records the old ID as an alias. Old-ID aliases are for migration and reference repair only; they should not participate in product classification vocabulary. Duplicate display labels may be allowed when scoped clearly by Product Type or group, but Configuration Review should warn when labels could confuse managers.
